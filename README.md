# Лабораторная работа 3. Ничего не забываем (Spring Data JPA, PostgreSQL, Flyway)

**Предметная область:** Информационная система управления спортивным залом (Gym Management System)

---

## 1. Стек технологий

* **Язык:** Java 21
* **Фреймворк:** Spring Boot 3.3.5
* **СУБД:** PostgreSQL 18 (в Docker-контейнере)
* **Доступ к данным:** Spring Data JPA + Hibernate ORM
* **Миграции БД:** Flyway (`flyway-core`, `flyway-database-postgresql`)
* **Контейнеризация:** Docker Compose (`postgres:18.4-bookworm`)
* **Тестирование:** JUnit Jupiter (JUnit 5), Spring Boot Test (`@SpringBootTest`)
* **Сборщик:** Maven 3.9+

## 2. Архитектура и управление схемой БД

Создание и изменение схемы базы данных выполняется **строго через SQL-миграции Flyway**.
Автоматическое создание или изменение схемы через Hibernate отключено:
```properties
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
```

### Версии схемы (Flyway):
1. **`V1__create_clients_and_memberships.sql`** — создание базовых таблиц `clients` и `memberships`:
   - Первичные ключи на основе `UUID` (`gen_random_uuid()`).
   - Внешний ключ: `client_id UUID NOT NULL REFERENCES clients(id) ON DELETE CASCADE`.
   - Индексы для оптимизации поиска.
2. **`V2__add_visits_and_preferred_locker.sql`** — содержательная эволюция схемы:
   - Добавление колонки предпочитаемого шкафчика в таблицу клиентов: `ALTER TABLE clients ADD COLUMN preferred_locker VARCHAR(10);`.
   - Создание таблицы посещений `visits`:
     - Внешние ключи на клиента (`client_id UUID NOT NULL REFERENCES clients(id) ON DELETE CASCADE`) и абонемент (`membership_id UUID NOT NULL REFERENCES memberships(id) ON DELETE CASCADE`).
     - Номер шкафчика `locker_number VARCHAR(10) NOT NULL`.
     - Отметки времени входа и выхода (`checked_in_at`, `checked_out_at`).
   - Существующие данные сохраняются в полном объёме.

## 3. Выполнение требований лабораторной работы

### 1. Персистентность данных
Все данные сохраняются в реляционной СУБД PostgreSQL 18. После перезапуска приложения данные остаются на месте (проверено вручную и через тесты).

### 2. Связи между ресурсами и целостность данных
- Связь «Один-ко-многим» (`@OneToMany` / `@ManyToOne`) между клиентами (`Client`) и абонементами (`Membership`).
- Связь между клиентами, абонементами и посещениями (`Visit`).
- Система проверяет существование связанных ресурсов и не допускает ссылок на несуществующие сущности (Foreign Keys на уровне БД + проверки на уровне бизнес-логики с выбросом 404/422).
- Удаление клиента или связанных объектов не нарушает ссылочную целостность базы данных.

### 3. Атомарные транзакции (изменение >= 2 связанных объектов)
- Операция перевода абонемента другому клиенту (`POST /api/memberships/{id}/transfer`): атомарно перепривязывает абонемент к новому клиенту с проверкой активности обоих клиентов.
- Операция входа в зал (`POST /api/memberships/{id}/check-in`): изменяет состояние абонемента (списывает визит у `VISIT_BASED`) и создает связанное посещение (`Visit`) с выделенным шкафчиком.
- Операции помечены `@Transactional`. При возникновении любой ошибки (например, целевой клиент заблокирован или передан недопустимый шкафчик) транзакция полностью откатывается (`Rollback`), ни одно изменение не сохраняется.

### 4. Эволюция схемы базы данных
- В проекте реализованы две последовательные версии схемы (`V1` и `V2`).
- `V2` содержит содержательное изменение структуры после первоначального создания (добавление поля `preferred_locker` и таблицы `visits`).
- Новая установка поднимает схему автоматически через Flyway, обновление существующей — накатывает миграции без потери накопленных данных.

### 5. Оптимизация выборки и решение проблемы N+1
- Реализован эндпоинт `GET /api/clients/with-memberships` (метод репозитория `findAllWithMemberships()`).
- Используется `JOIN FETCH` в JPQL-запросе, что гарантирует загрузку клиентов вместе с их абонементами за **ровно 1 SQL-запрос**.
- Поведение протестировано на выборке из десятков объектов (генерация через `POST /api/clients/seed` и интеграционный тест `shouldFetchListWithRelatedEntitiesWithoutNPlusOneQuery`).

### 6. Тестирование
- **Юнит-тесты бизнес-логики (19 тестов):** выполняются **без запуска Spring-контекста** за доли секунды (чистые POJO-тесты с in-memory репозиториями на динамических прокси).
- **Интеграционные тесты БД (6 тестов):** проверяют персистентность связанных объектов, целостность внешних ключей, корректный откат транзакций при сбоях и отсутствие проблемы N+1.

## 4. Инструкция по запуску

### Шаг 1. Запуск PostgreSQL в Docker
```bash
docker compose up -d
```
БД доступна на `localhost:5432` (пользователь `postgres`, пароль `postgres`, база `postgres`).

### Шаг 2. Запуск приложения
```bash
mvn spring-boot:run
```
Приложение запускается на порту `8080`. При старте Flyway автоматически накатывает миграции `V1` и `V2`.

Для автономного запуска без внешнего Docker PostgreSQL поддерживается локальный профиль:
```bash
mvn spring-boot:run -Dspring-boot.run.arguments="--spring.profiles.active=local"
```

### Шаг 3. Запуск тестов
```bash
mvn test
```
Все 25 тестов (19 юнит + 6 интеграционных) проходят успешно.

### Шаг 4. Прогон сценариев через curl-скрипт
```bash
bash requests.sh
```
Скрипт проверяет все сценарии, валидации, откат транзакции и детальную выборку без N+1.
